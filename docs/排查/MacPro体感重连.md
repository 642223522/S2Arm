# Mac：Switch 兼容 Pro 的体感在底座重连后失效

## 症状与已确认原因

原始复现环境：Apple M4、macOS 26.6.2、第三方 Switch 兼容 Pro、USB 2.4 GHz 接收器和充电底座。原场景不是 Bluetooth 直连，也不是 Switch 2 Pro。底座令手柄断连，接收器保持插着；取出后按键仍可用，体感可能停更或持续全零。

公开 `GameController` 查询得到：`motion != nil`、`hasRotationRate=1`、`hasGravityAndUserAcceleration=0`、`sensorsRequireManualActivation=1`、`sensorsActive=0`。旧前端把“可用的校准样本”与“可控制传感器电源”混为同一条件，在缺少分离重力能力时把整个 motion profile 丢掉，因而从未提交公开的传感器开启请求。

macOS 的 `JoyConHIDServicePlugin` 运行在 WindowServer 中。系统日志能看到它的初始化、`Disable IMU`，以及公开 API 请求后的 `Enable IMU`。一个只通过 `sensorsActive` 控制、HID 被动观察的短实验中，原始值按“全零 → 约 1 g / 有角速度 → 全零”变化；没有手写 HID 配置命令。这说明应当把需求交给公开控制接口，而不是根据别人的 ACK 猜测初始化结束、反复重发 `0x40`。

该接收器的公开校准数值仍为零，尽管原始 HID 样本有效；系统日志另有校准读取错误。本修复不声称修好了 macOS 的校准管线，也不把全部校准错误归因于 S2Arm。仍保留现有原始样本路径，不伪造公开样本为可用。

## 与 PR952 的关系

- PR952（`92d2236a`）把一代 HID 存储改成按设备记，消除了 0.3.10 中左右各一格、同 PID 接口互相顶替的一种问题。
- 它仍按 VID/PID 接受该接收器的两个接口，并保留上述校准能力过滤与原始 IMU / 模式配置；启动器的观察器不启用 Pro 传感器。
- 已安装的 0.3.10 源码是旧布局，不包含 PR952，不能把该版本的运行当作对 PR952 的验证。
- 使用精确 PR952 前端和驱动、持续六轴请求的本地原生宿主探针，30 秒完整底座循环仍重现：约 8 秒断连、15 秒重连，之后 15 行汇总均为零、`active=0`。这是原生路径验证，不是完整游戏 / C# 服务层验收。

## 修复边界

1. 控制源按游戏需求选择整个 `GCMotion`，不受校准数据能力过滤；是否发布公开数值仍沿用原来的能力判断。P1 和后续槽位共用同一电源选择规则，换源、关闭及共享源不重复开关。
2. 对原始 Pro 接口调用公开 `+[GCController supportsHIDDevice:]`，把结果缓存到本次连接。框架声明支持时，选择公开传感器控制后端，S2Arm 的 HID 驱动不再直接发 IMU `0x40` 或报告模式 `0x03`。这是一项后端选择，不是“独占硬件”的声明；不能用 `DeviceOpenedByEventSystem` 代替该 API，本接收器上该属性缺失。
3. 设备支持不等于输入接口可用：本接收器的 joystick 接口和 vendor 接口都得到 YES。因此另外解析 HID 描述符，只有声明 Nintendo `0x30` 或 `0x3f` 输入报告的接口才进入原始读取与设备 ID 表。输入只读接口可接受；描述符缺失、截断或不可解析时保留原尝试，不按厂商名加白名单。
4. 原始读取只返回请求开启且 250 ms 内更新的样本。错误或旧接口的回调不能覆盖当前连接的样本。
5. 连接初始化时，锁内复核设备指针、连接代号及当前需求，预留包序号并复制完整输出包，retain 目标后解锁，再做同步 HID 写入。后续命令重新复核，避免 detach 或同一设备 / 槽位重新连接后继续发送旧初始化命令。已开始的写入可能因拔出而失败，但不会从被复用的槽位取到另一个目标。

一代 Joy-Con 的原始控制、框架不识别的 Pro 原始控制、NS2 通道、震动编码和玩家分配规则不在本修复中重写。震动路径仍可能使用 HID；审计的零写入只指 Pro 的 IMU / 报告模式命令，不是“USB 上没有任何配置流量”。

## 复测与读数

| 原生宿主变体（同一接收器） | 完整底座循环 | 结果 |
| --- | --- | --- |
| 未改的 PR952 | 1 次，30 秒 | 重连后持续全零、公开请求 `active=0` |
| 基于注册表属性的临时版本（已弃用） | 1 次，30 秒 | 运动恢复，但审计发现 6 笔直接配置；不计为零写入设计通过 |
| PR952 + 本修复，公开支持 API 选择后端 | 1 次，30 秒 | 重连后 `active=1`、持续变化的原始值、1188 次采样时观察到时间戳变化、Pro 直接 IMU / 模式配置写入 0（包括关闭） |

另有一次 20 秒 PR952 采集没有确认完整断连 / 重连，不计入循环验收；早期手动和 ACK 补发实验不是最终修复。

该表的宿主探针使用同一 PR952 快照，补丁变体只替换修复相关的生产代码。日志中的 `samples` 是采样时观察到的变化次数，不是 HID 报告总数。两个有效循环各只跑过一次，不能推导长期崩溃率、所有接收器兼容性或完整游戏已通过。

## 扩展检查：通过项与现存缺口

以下为同一 Apple M4 / macOS 26.6.2，实现提交 `396414b3` 的本地原生前端检查。宿主保留真实 `sample_input` / 六轴读取 / 默认内存玩家分配，用合成平台接缝替代游戏和 C# 服务层；无震动或完整游戏验收。

| 连接 / 变体 | 分母 | 期望 → 真结果 |
| --- | --- | --- |
| 同一第三方 Pro，USB 接收器实际拔插 | 1 次完整循环，30 秒阶段 | 自动恢复 → 11.639 秒旧接口移除，18.201 秒新接口 / profile 出现，19.204 秒有重力读数，需求关闭前已观察到明显角速度；22 / 24 秒需求关 / 开有效，直接 IMU / 模式调用始终 0 |
| 同一第三方 Pro，直接 Bluetooth | 1 次完整循环，29 秒阶段 | 自动恢复 → 8.343 秒移除，15.309 秒新连接，16.325 秒 P1 有变化的运动；18–21 秒有按钮，需求关 / 开有效，直接 IMU / 模式调用始终 0 |
| 第三方原代兼容左右 Joy-Con，无 Pro | 本补丁 1 次完整左侧循环，60 秒阶段 | 双流持续可用 → **未通过**。左 16.060 秒断开、36.296 秒新接口，45–51 秒两路运动和按钮到达 P1；右此前有缺口，58.922 / 59.932 秒又过期，仅剩一路。需求关闭后两路均不发布，重新开启后曾恢复两路 |
| 同一 Joy-Con 对，精确未修改基点 `00825011` | 1 次完整左侧循环，60 秒阶段 | 双流持续可用 → **同样未通过**。右约 28.7 秒起丢失全报告，重连附近短暂再有全报告，随后持续简单报告；前端仍把长达 17.157 秒未更新的运动当成有效 |

Joy-Con 在系统设置里断开 / 重连耗时较长，用户为这两次对照明确放宽至 60 秒计时阶段，初始化 / 退出另记；补丁侧为 1 ms / 2.731 秒，基点侧为 1 ms / 15.038 秒。仓库 `tools/pro_motion_probe.sh` 的 30 秒上限没有改变。更早的 29 秒 Joy-Con 采集未包含左侧重连、且 Pro 仍在线，不计隔离双 Joy-Con 的循环验收。

基点的原始回调诊断显示：右接口在 36.687–51.826 秒的 `0x30` 计数保持 1611，`0x3f` 从 761 增至 1742；回调持续收到，错误、sender 不匹配和短全报告计数均为 0。基点没有本补丁的回调拒绝规则，因此已经证明一种原有的全报告供给缺口，不是仅凭补丁后 `known=0` 推断。基点读取器又把旧样本继续作为有效值发布；本补丁的 250 ms 判据会暴露过期状态，不能把恢复旧的无限保留值当作“体感修好”。

写入成功也不等于手柄已按预期开启：基点在 54 秒再次提交的两只 IMU / 模式写入均返回成功，右仍持续 `0x3f`；退出时左模式写入另返回 `kIOReturnTimeout`，耗时 5.001 秒。本组数据没有辨识谁改变了报告模式，也不能证明补丁侧每一处缺口与基点同因；不据此加 ACK 补发或猜测延时。

**混用是另一项现存路由缺口**：一次早期实物采集看到 P1 Pro 接收原始 Joy-Con 运动、P2 Joy-Con 无六轴。随后同一原创合成夹具分别编进精确基点与补丁的生产前端 / 读取器，两个变体均为 2 条断言中 2 条失败：P1 为 Pro 时，期望自己的单路样本，实际得到另一玩家左右两路；Pro 放 P2 时，原始样本存在，实际返回 0 路。夹具不访问设备、不运行游戏。这证明相关路由缺口在基点已有，并非混用兼容已通过；本 PR 只验证 P2 的公开传感器电源选择，不声称解决每槽原始六轴归属。

结论：增加了这只第三方 Pro 的接收器拔插与直接 Bluetooth 覆盖；Joy-Con 完整循环虽恢复过双流，但持续性未通过，混用的路由仍需另修。不能把本修复描述成所有 Pro / Joy-Con / 混用组合通用通过。

## 变基后的验证范围

分支首次变基到 `origin/main` 基点 `701d7aaebb8083afd240eb4d6407dda5671394e4`，保留上游新增的分玩家键位映射。变基当时，原始 HID 驱动、公开电源 helper 及 P1 / 后续槽位的运动采样代码与实物测试提交 `396414b3` 相同；前端其余部分已随上游更新。下面的评审修正随后改变了原始驱动的连接初始化实现，原硬件日志不覆盖该修正，也不能写成新基点的实物通过。

变基时重新运行：生产代码边界检查 30 条、实际原生输入套件（含上游分玩家映射）、检查接线、文档单测 24 条均通过。另将同一无设备判据分别编进精确新基点和本补丁的生产前端：partial profile 应请求传感器，基点 `active=0`、补丁 `active=1`。这项对照不依赖手柄或游戏，也不能替代实物回归。

公开电源 helper 由所有 GameController motion profile 共用，并非仅影响 Nintendo 手柄。若 Xbox profile 的 motion 为 nil，不会提交传感器开关；其他带 motion 的控制器仍受新选择规则影响。原装 Nintendo、Xbox、PlayStation 等手柄均未做实物回归。公开支持查询只保证关联 GCController，不能保证 motion 存在；框架识别 Pro 却始终没有 motion 时，当前补丁仍会跳过直接 IMU / 模式配置，这是尚未排除的兼容风险。

## 评审修正：连接时的同步写不占采样锁

#1092 评审指出，首次提交 `a6ef6dcb` 的 `attach_device` 持 `g_mu` 调用同步 `IOHIDDeviceSetReport`，扩大了原有锁范围。游戏侧六轴、按设备六轴、按键和按键原始报告读取都使用这把锁；连接原始控制设备时，写入等待会阻止这些读取。

修正只处理连接初始化：每条命令在锁内检查设备及本次连接代号、重读 `want / pad_want` 和缓存的后端选择，复制命令并 retain 目标，解锁后发送，返回后 release。连接代号不随槽位清零而复用；原始控制的命令内容与包序号规则不变。其他原有开关需求、震动发送路径未在此轮重构。

Apple M4 / macOS 26.6.2，无设备生产代码检查：新增 8 条后，修前 38 条中 6 条失败；修后 38 条全部通过。同步输出替身内可取得 `g_mu`，并完成四个生产读取函数的调用；另覆盖输出期间 detach、同指针 / 槽位重连、需求结束、目标引用配平、按钮专用初始化和被动 Pro 后端。负对照恢复持锁输出为 6/38 失败，只去掉连接代号核对为 1/38 失败。这些是锁与生命周期判据，不是真机蓝牙写耗时或原装手柄验收；本轮没有新增硬件循环或原装描述符 dump。

## 独立检查（无需游戏、着色器或完整 App 构建）

```sh
bash tests/macos_pro_motion_test.sh
bash tests/macos_native_input_test.sh
```

前者包含真实生产代码，替换 IOHID / 框架支持查询的边界，不接真实设备；后者还验证实际前端的能力过滤、P2 控制及 NS2 优先级。编译不代替实物读数。

只测一只 Pro 时，可使用小探针（默认 20 秒、最大 30 秒）：

```sh
bash tools/pro_motion_probe.sh 20 2> "$HOME/Downloads/pro-motion-native.log"
```

先关闭其他手柄应用，让手柄通过原来的接收器连上、离开底座，再运行；倾斜、放入底座直到断连、取出重连后再次倾斜。不发手动 `i`、不重置，也不更换连接方式。临时可执行文件退出后清理。探针不会替换已安装的 S2Arm，也不读取游戏库、存档或密钥。

`raw_config_writes` 只统计 S2Arm 原始 Pro 驱动直接发送的 `0x40 / 0x03`，不统计系统驱动内部配置或其他手柄的 legacy 控制。公开提交前检查日志，不附设备序列号、MAC、注册表 ID、本机路径或原始报告。

## 未验证

- 完整游戏、长局、其他 macOS 版本、原装 Pro（含 Bluetooth）、多个 Pro 混用的实物效果；上节仅验证同一第三方 Pro 的直接 Bluetooth。
- 非 Nintendo 控制器的实物输入 / motion 回归；共享前端测试不代表这些硬件已经验证。
- 第三方 Joy-Con 的全报告连续性、报告模式改变来源，以及上述每玩家原始六轴路由缺口：已观察到问题，尚未修复，不能记成“未遇到问题”。
- 框架识别 Pro 但不提供 motion profile 的平台组合：本修复不强行绕过所选框架后端，不保证其体感支持。
- 系统校准失败原因、其他应用同时修改同一设备时的仲裁，以及震动协议事务的并发行为。

公开接口依据：Xcode SDK 的 `GCMotion.h`（手动激活要求与样本能力分别定义）、`GCController.h`（设备支持查询有缓存要求）。没有调用 Apple 私有插件 API。
