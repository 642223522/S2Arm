# 日志与机器事件规范

本文是后续日志实现与消费者迁移的目标设计。JSONL 包络和事件目录仅作为 `docs/standards/` 中的设计资料，**本 PR 不修改任何运行时输出或现有消费者**。生产者与读取器继续遵守[真机契约](../../tests/真机契约.md)，`S2A 标记 MARK：帧 N`、`[声]`、`【首遇】` 等现有中文标记必须保留原样。下面的要求只约束以后另开 PR 的日志实现与迁移，不表示已接入 JSONL、双输出或完整性校验。`MUST`、`SHOULD` 及维护权限见[仓库规范](repository.md)。

## 输出职责

| 文件 | 职责 | 后续实现要求 |
|---|---|---|
| `host.log` | 人读诊断记录 | 可保留第三方原始行、堆栈和上下文；中文文案可读，不承担新机器协议 |
| `events.jsonl` | 稳定机器事件接口 | UTF-8，每行一个完整 JSON 对象；事件名、版本和 typed data 由 catalog 定义 |
| `frames.tsv` | 现有逐帧测量 | 保持现有列、采样位置和热路径；不得为了 JSONL 在每帧追加格式化与分配 |
| `run.json` | 一局的元数据与格式声明 | 记录运行标识、构建／平台／配置来源、日志协议模式及收局状态；与事件流共同校验完整性 |

事件包络见 [log-event.schema.json](log-event.schema.json)，事件设计目录见 [log-events.json](log-events.json)。只有被机器消费、参与验收或需要稳定关联的事件才进入 catalog；普通 DEBUG 文本不必登记。所有条目均为 `planned`，不表示生产者已经输出或消费者已经采用；校验这些资料的工具也只供开发者手动使用。

日志不得包含密钥、存档正文或游戏资源内容；诊断路径按需要记录，不能把个人绝对路径当成接口的一部分。输出目录由执行器／调用方传入，源码与运行数据的边界见[仓库规范](repository.md)。

## 事件包络

字段的精确类型与必填约束以 schema 为准；下表解释语义，不能通过自由文案替代字段。

| 字段 | 语义 |
|---|---|
| `schema_version` | 整个事件包络的版本，当前为 `1`；消费者按支持的版本解析 |
| `event`、`event_version` | 验收记录必需的稳定事件名及该事件 typed data 的版本 |
| `run_id` | 起局时生成且本局不变的运行标识；重启属于新局 |
| `source_id` | 本局内唯一的生产者流标识；多进程或 writer 重启后不能复用而重置序号 |
| `seq` | 同一 `source_id` 的 writer 写出序号，单调递增；不代表跨线程业务发生顺序 |
| `timestamp` | UTC 墙钟时间，使用带 `Z` 的明确格式；用于定位，不用于计算窗口时长 |
| `elapsed_us` | 从本局统一 native 单调时钟基准起的微秒数；原生层和 C# 使用同一基准，不能各自从启动计时 |
| `level` | 固定日志级别，见下节 |
| `component` | 稳定组件标识，用于定位责任模块，不拼接动态业务参数 |
| `pid`、`tid` | 可获得时记录事件生产者的进程／线程标识，不能误填异步 writer 的线程号 |
| `source_file`、`source_line` | 源码定位可用时携带文件和行号；不得编造未知位置 |
| `message` | 供人阅读的上下文，可随表达改进；消费者不能匹配此字段判格 |
| `data` | catalog 定义的 typed object；数值、布尔值与枚举保持类型，不把单位或结构藏进字符串 |

MARK、声音窗口、画面检查等依赖帧或窗口的事件 MUST 在 `data` 中显式携带 catalog 规定的帧号／窗口标识及必要边界。不能用日志相邻、UTC 时间相近或 `seq` 大小推断跨线程因果关系。涉及多进程时，执行器须分发同一单调时间基准或明确可验证的换算关系；未建立关系的读数不能直接对齐。

事件名与字段语义一经消费即为接口。更改类型、单位、必填项或含义 MUST 升相应版本，并在同一迁移计划中更新生产者、读取器与验收。新增可选信息是否兼容按 schema 与消费者规则判断；不能保留原版本后改变含义。catalog 变更须由生产者维护者与测试出包线共同审查。序号、时长等 64 位整数 MUST 无损读取，JavaScript 消费者不能直接经 `Number` 丢失精度。

## 级别与验收

| 级别 | 用途 |
|---|---|
| `DEBUG` | 默认可关闭的开发细节；必须控制频率与成本 |
| `INFO` | 理解正常运行所需的重要状态，如就绪、窗口起止 |
| `WARNING` | 异常但尚不足以确认功能失败的情况；写清后果 |
| `ERROR` | 已发生、需要处理的问题；进程是否继续由接口明确决定 |
| `FATAL` | 项目主动判定无法继续，记录后终止进程；不得用作普通错误标签 |

外部崩溃由崩溃事实事件表达；收到信号不等于常规 logger 有机会写出 `FATAL`。级别本身不直接决定红绿格：验收读取事件及其 typed data，并按契约判断。中文文案、`【红】`、颜色、emoji 和第三方前缀均不能成为新协议。

迁移 MUST 保留现行语义，尤其是以下边界：

- `tools/redline.py` 默认把“出图未满屏”排除通用报红，只影响画面格；空“未实现服务：”是零项汇总，不计红。非空未实现项和其他真实失败仍按现有契约处理。
- `tools/game_fps.py` 使用最后一条有效帧节拍记录。`graphics/loop/RenderLoop.cs` 正常收局时会补写本局占时最多的交换间隔，所以末条不一定是最后一次间隔变化；catalog 的 `basis=change|run_dominant_summary` 区分两者。交换间隔 `0` 按 `60` 帧／秒判。缺少帧节拍时返回的 `60` 只是计算占位，`ok=False`；`tools/score_cells.py` 据此判口径无效、不写格，不能变成已测 60 帧或绿色。
- 缺少满屏开关、声音读数、必需的逐帧列或其他验收证据，继续按各格现有“未测／无效”规则处理，不以没有 ERROR 代替通过。

验收所需事件 MUST 独立于 DEBUG 过滤和普通诊断采样；关闭 DEBUG 不得删掉就绪、MARK、失败、帧节拍等判据。临时调试日志不能靠提升到 ERROR 强制保留。

## 并发、性能与完整性

后续 logger MUST 使用有界队列，并在字符串格式化、JSON 编码和昂贵采集之前执行过滤、限频或采样。渲染、信号和锁敏感路径不能等待日志磁盘 I/O。`frames.tsv` 仍由原测量路径输出；低频事件需要复用帧号，而不是复制逐帧采样。

丢弃必须可见：writer 须按生产者及事件类别累计 drop，记录原因、覆盖范围和数量；验收事件与普通诊断事件须可区分。正常收局须有结束记录与完整性账本，至少可核对生产／接受／写出／丢弃数量、最后序号与各输出状态。队列满、写失败、截断、缺行、序号断裂、缺结束记录和未闭合窗口都不能被当成“没有错误”。具体队列容量、背压策略和账本字段由运行时实现 PR 明确并验证。

结构化通道失败时，依赖它的格 MUST 标为证据不完整或局无效，不能继续判绿；不依赖该证据的格按各自契约处理。双输出期间 MUST 明确报告 `host.log` 与 `events.jsonl` 的独立写入状态：JSONL 失败不能静默回文本，两个输出都失败时应通过退出状态、执行器状态或独立收局元数据暴露。不能把失败通知仅写回已经失败的通道。

正常退出应完成排空和收局；崩溃现场只能尽力保留，不能承诺所有缓冲都已刷盘。完整性校验必须能识别异常终止留下的有效前缀与缺失尾部，并将未完成证据传给判格器。

## 信号与崩溃现场

信号处理器 MUST 使用独立、预分配的 async-signal-safe 原始记录通道；不调用常规 logger、分配器、锁、JSON 编码、托管代码或非安全的格式化函数。原始记录只捕获能够安全取得的最小现场和关联标识，写入预先准备的目标；详细线程现场和符号化在安全上下文尽力补齐。

执行器或收局工具可将原始记录后处理为 catalog 定义的崩溃事件，同时保留原始文件和转换来源；不得把后处理时间冒充崩溃发生时间，也不得伪造无法恢复的 `seq`、线程或寄存器值。logger 本身不可用不应阻止最小崩溃证据收集。此通道及其格式在后续实现 PR 单独验收。

## 分阶段迁移与验收

1. **设计与自愿工具（本 PR）**：确定本文、schema、首批 catalog 和开发者自查入口；保留现有 App、执行器和判格行为，不新增门禁。
2. **生产者与双输出（后续）**：清点原生层、C#、平台外壳及执行器的生产者，为每条机器标记列出来源、事件版本、频率、消费者和影响的格；实现统一时钟、队列、完整性与崩溃通道，并实测开销。
3. **读取器与判格迁移（后续）**：逐个事件先实现双输出，再覆盖 `dev_run.sh`、`redline.py`、`game_fps.py`、`score_cells.py`、健康表、里程碑及其间接读取器，逐条核对“生产者 → 读取器 → 判格”链。每个事件单独验收，全部消费者切换且旧实现反证通过后才具备清理旧输出的条件。
4. **清理旧接口（后续独立 PR）**：明确兼容期限与旧数据支持策略，提供消费者已全部迁移、双输出对照和旧实现反证的证据后，才删除对应中文行；历史局仍由显式 legacy 读取器处理。

`run.json` MUST 明确日志协议模式与版本，旧局通过显式 `legacy` 模式选择旧读取器。新的结构化局如果文件缺失、JSON 损坏、版本不支持或完整性失败，必须报协议／证据错误，不能猜成旧局并回退匹配文本。没有 `run.json` 的历史目录须由调用方显式选择 legacy，不伪造历史元数据或历史 JSONL。

迁移验收 MUST 同时使用保留来源的真实历史日志 fixtures 与真实的新运行。历史 fixtures 验证旧读取器语义；真实新运行在双输出期间对同一局分别运行新旧读取器，逐格比对结果、原因、数值、窗口和“未测／无效”状态。发现差异先定位生产、转换、读取还是判格规则，不以只比最终红绿或修改期望值通过。不得根据文本猜造“历史 JSONL”后声称完成运行时兼容验证。

以上是后续 PR 的验收条件，本 PR 的 catalog/schema 校验不构成运行时日志、设备或游戏验证。

## 公开参考与项目决策

[Abseil Logging](https://abseil.io/docs/cpp/guides/logging)公开说明了日志级别、上下文以及 FATAL 终止语义，可作为设计参考。S2Arm 的 DEBUG 级别、JSONL 包络、事件 catalog、完整性账本和判格映射均是本项目设计，**不是 Google 内部日志协议，也不表示项目已采用 Abseil 库**。
