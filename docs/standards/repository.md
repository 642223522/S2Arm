# 仓库结构与贡献规范

本规范帮助贡献者确定代码放在哪里、由谁审查、怎样提交可验证的改动。`MUST` 表示合入要求；`SHOULD` 表示通常应遵守，偏离时须在 PR 中说明理由、影响与验证。规则变更由相关目录维护者审查；涉及构建、门禁或判格时，测试出包线必须参与。个人偏好不能作为新增合入要求。

首个工程规范 PR 只建立文档、日志设计资料与开发者自愿使用的格式／静态工具。风格建议不新增合入门槛，也不接入门禁、列车或出包；以后是否接入门禁须另开 PR 决定。运行时结构化日志、消费者迁移和目录搬迁分别在后续 PR 实施，不能用本规范推断这些工作已经完成。

## 目录与归属

当前源码仍以仓库实际路径为准。[多终端架构方案](../架构_多终端.md)规定目标分层；下表是阅读和后续迁移对照，不是本 PR 的搬迁清单。

| 当前路径 | 目标路径 | 职责与审查归属 |
|---|---|---|
| `runtime/src/`、`runtime/include/` 中平台无关部分 | `core/native/` | 原生执行核心；原生层线 |
| `runtime/rewriter/` | `core/rewriter/` | 出包期改写；原生层线 |
| `services/` | `core/services/` | 系统服务接入；原生层线 |
| `graphics/loop/`、`graphics/track/`、`graphics/widen/` | `core/gpu/loop/`、`track/`、`widen/` | 显卡公共逻辑；渲染器／画幅对应线 |
| `runtime/tests/` | `core/tests/` | 原生核心测试；原生层线 |
| `graphics/metal/` | `backends/metal/` | Metal 后端；渲染器／着色器对应线；iOS 出图层另归外壳 |
| `graphics/ohos/`（相关平台分支） | `graphics/vulkan/` | Vulkan 后端；鸿蒙／安卓贡献者与显卡对应线 |
| 苹果与 Linux 系平台调用、现有 `platforms/` | `platform/plat.h`、`apple/`、`linux/` | 公共平台接口与实现；原生层线及对应平台维护者 |
| `ios/`、Mac 宿主入口及各平台外壳 | `platforms/ios/`、`macos/`、`android/`、`ohos/` | 窗口、输入、生命周期与签名入口；对应平台维护者 |
| `graphics/tools/` | `tools/shader/` | 出包期着色器工具；画面·着色器线 |
| `pack/` | `pack/common/` 与各终端子目录 | 公共出包阶段与终端出包；测试出包线 |
| `compat/` | 保持 | 锁定上游、补丁、真值工具；按 [Ryujinx 流程](../../compat/README.md)维护 |
| `tools/`、`tests/`、`docs/` | 保持 | 长期工具、测试及文档；按具体设施与接口归属审查 |

新增平台代码 MUST 按架构方案选择职责层；公共核心 MUST 通过平台接口调用平台能力，不能增加假装另一平台可用的替身头。未完成迁移的现有调用仍需在独立的平台接口 PR 中处理。模块构建细节 SHOULD 留在各自的 `build.mk`，顶层 `Makefile` 作为公共入口。

## 工具、脚本与实验

| 路径 | 长期用途 |
|---|---|
| `tools/` | 可重复运行的构建辅助、开发诊断、门禁、调度与收局工具；公共入口应有参数、失败状态和使用说明 |
| `pack/` | 从输入资源到可部署包的流水线，区分公共阶段与终端阶段；构建工具不能顺便成为长期运行数据目录 |
| `tests/` | 自动化测试、真机契约、路线与经过许可的测试资产；测试说明要区分主机检查、真机运行与判格证据 |
| `scripts/` | 保留现有脚本与已有调用方；新增长期能力优先放入上述对应目录，避免继续堆放职责不明的脚本 |
| `experiments/` | 后续实验的建议位置；只在有具体实验时创建。每项实验写明假设、入口、资源需求、结果与是否保留，不作为产品或门禁的隐式依赖 |

复用现有能力是 MUST。把实验提升为长期设施时，须明确维护者、文档、调用入口与验证，再在独立 PR 中迁移；不能只复制到 `tools/` 后留下两套实现。存量 `scripts/` 不在本 PR 批量搬迁。

## 源码、产物与运行数据

可重建的编译和出包产物 MUST 与源码分开，默认落在仓库 `build/` 或已约定的被忽略构建目录。外置 `run/` 保存局目录与运行证据；游戏资源、固件、密钥和存档应各自独立保存，不能混入源码、构建缓存或可整体清理的实验目录。具体输入、设备 Documents 布局和存档注入以[真机契约](../../tests/真机契约.md)为准。

新工具 MUST 通过参数、已声明的环境变量或项目配置取得资源根、存档根与局目录，不得硬编码个人用户名、主目录或某台机器的挂载路径。文档示例使用 `<资源根>` 等占位符。现有文档中的个人路径是历史环境记录，不能作为新的接口默认值。

清理 MUST 只操作明确归属、可重建或用户指定的目标，保留输入资源、存档及他人的局目录。进程组信号仍只经 `tools/safe_killpg.sh`；禁止危险的负 PID 广播、直接清空共享运行根以及在门禁／测试内联网。游戏文件、固件和密钥不得入库或在 PR 分发。

## 接口、第三方代码与 PR

公共 C ABI、C# 互操作声明、数据结构布局、平台接口和测试契约的改动 MUST 由接口两端维护者共同审查；生产者、调用方、文档及相关验证须在同一可审查变更中同步。不要把自动格式化造成的差异误认为 ABI 兼容证明。

第三方代码 MUST 保留来源、版本和许可证；不要用项目格式器批量改写 `compat/tree/` 或 `graphics/third_party/`。Ryujinx 改动仍直接修改 `tree/`，用 `compat/patch_new.sh` 生成补丁、登记 `series` 和改动清单，四者同一提交，并通过 `compat/verify.sh`。格式排除不代表免除补丁一致性与功能审查。

贡献者 MUST 在分支提 PR，不直接推 `main`；合入沿用[贡献指南](../贡献指南.md)的对口线、整套门禁和列车流程。格式化、功能变化、目录搬迁 SHOULD 分开 PR；目录搬迁须提供旧路径到新路径对照与构建／出包路径验证。共用目录改动须说明对现有苹果路径的影响和证据。

PR 说明 MUST 写清问题、最终行为、验证命令与结果、尚未验证的条件。构建成功、出现窗口、真机起局、达到代表场景和游戏可玩是不同证据，不能相互代替。代码质量检查见[风格规范](style.md)，日志协议及迁移要求见[日志规范](logging.md)。

规范采用“降低维护复杂度、方便读者、规则有实际收益”的原则，参考 [Software Engineering at Google：Style Guides and Rules](https://abseil.io/resources/swe-book/html/ch08.html)；审查同时关注设计、行为、复杂度、测试与文档，参考 [Google 代码审查指南](https://google.github.io/eng-practices/review/reviewer/looking-for.html)。具体目录和门禁规则是 S2Arm 的项目决策。
