# S2Arm 贡献指南（联合开发者）

首次参与请先读根目录的[贡献指南](../CONTRIBUTING.md)。新联合开发者的入门指引（规则、自检、边界、红线、可领任务）见[协作入门](协作入门.md)。本页保留联合开发者的分工、内部协调和合入约定；AI 辅助贡献另见 [LLM 使用政策](../LLM_POLICY.md)。

欢迎！想让 AI 定时领任务、提 PR、按评论修改，请看 协作循环。**动手前先翻 [坑记录](坑记录.md) 和 研究**，我们踩过的坑和结论都在里面。再读[仓库规范](standards/repository.md)、[代码风格](standards/style.md)和[日志规范](standards/logging.md)。当前源码路径见 [README](../README.md)；[多终端架构方案](架构_多终端.md)中的 core / backends / platforms / pack 是后续目标目录。

- 唯一登记：`tools/layer_map.tsv`（每个仓库文件属哪层、哪个模块、谁该跟进），`python3 tools/layer_map.py which <路径>` 查单个文件。

### 目标图（还没落地，别当成现状）
- **目标**：直连 Vulkan 从 `android/native/` 归位到 `graphics/vulkan`，安卓、鸿蒙共用。
- **目标**：Linux 族宿主原语（页、时钟、线程）从安卓私有实现里抽出，放到 `launchers/linux` 下供安卓、鸿蒙共用；现在 `launchers/linux` 只是启动器原型。

## 提交流程
0. **先读 [快速测试与精修流程](快速测试与精修流程.md)**：怎么用一条命令在 4–5 分钟内测一款游戏（`tools/quicktest/one_game.sh`）、单款怎么定位第一失败点和根因、诊断开关与真值对拍、维护方踩过的坑。别拿完整出包加真机去验每一次改动。
1. **不要直接推 main**。在本仓库开自己的分支（建议 `<平台>/<主题>`，如 `android/vk-surface`、`mac/launcher`），提 PR；草稿 PR 也欢迎，先对齐结构。
3. 改到共用目录（core/、backends/metal、pack/、tools/、tests/）时，在 PR 说明里写清改了什么、为什么，以及怎么证明苹果路径不受影响（产物逐字节不变或读数一致）。
6. 提交说明建议采用 `fix(native): 修复地址窗口探测` 形式，写清类别、模块和具体动作；PR 写问题、改动、实际验证和限制。规范及日志协议变更由相关维护者与测试出包线审查。
7. 新源文件带 `SPDX-License-Identifier: Apache-2.0` 和 `Copyright <年份> S2Arm contributors`。不要给存量文件批量补头；第三方文件保留原许可头。说明见根目录 [CONTRIBUTING.md](../CONTRIBUTING.md) 的「许可证与 SPDX」。
8. **修好了「强信号」登记过的问题，在修复 PR 里删掉 [docs/名单_能力强信号/](名单_能力强信号/) 里本款文件 `<程序号>.tsv` 对应那行（文件删空就删文件）**，并写明复测依据（真机局或 `tools/ab_pair.sh` 对照局的报告）。
   强信号 = 某款某版本某项能力（满屏 / 60 帧）已知坏，出包把这项关掉。实现文件改了，这条不会自动撤，只会标「过时·待重新实测」并保持关，
   进复测清单（`python3 tools/caps_policy.py retest`）；修没修好只有改代码的人清楚，所以由修复作者删行。不加门禁检查。

9. **分支要短**：一个 PR 只做一件事，目标几小时内合入；做不完就拆成几个能各自验收的 PR。24 小时没合入，巡检提醒「合最新 main 或拆小」；48 小时标 `待拆`，维护者先拆出能独立合的那块。细则见协作循环 §3.4。
10. **main 红了先修 main**：谁的合入弄红了 main，谁当轮修，修好前同一块不再堆新改动；main 某步连续红超过 12 小时，升级报维护者。

## 安全规矩（门禁会查）
- 给进程组发信号只能经 `tools/safe_killpg.sh`；不许 `kill -1`、`kill -- -<算出来的组号>`、`pkill -g`。
- 不许 `rm -rf` 共享目录（run/s2arm 下别人的产物）；不许在门禁 / 测试里联网。
- 游戏文件、固件、密钥不进仓库，也不在 PR / 评论里分发；玩家自备正版。
